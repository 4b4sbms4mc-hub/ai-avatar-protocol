AIAP Avatar Core 白皮书

多成员容器与分域记忆架构

AI Avatar Protocol  \|  v0.4.2 修订草案公开作者：Wang Lu2026年9月19日

摘要

AIAP 定义由用户控制、可验证、可迁移的个人 AI 状态层。模型和执行平台可以更换，用户的身份、偏好、重要记忆与长期形成的工作方式应在授权范围内保持连续。本版延续 Spindle Architecture：Personal State 与 Procedural State 可以持续增长，中间的 Avatar Core 只保存必要核心状态、索引和可验证引用。

v0.4.2 在 v0.4.1 基础上补充 Multi-Core Container / Avatar Bundle、Shared Space、个人生活与工作隔离、组织业务归属、分层记忆治理及分范围迁移。一个文件可以装载多个成员的 Core，但物理聚合不合并身份、控制权或访问权限。

记忆沿用 State Model v0.1 的 M0、M1、M2、M3 逻辑层；本版明确其与访问范围、对象状态、Runtime 缓存冷热的区别。第一阶段以单成员参考实现验证这些边界，家庭和公司的完整管理功能分阶段实现。

1 协议边界与纺锤架构

1 1 目标与边界

AIAP 负责 Identity、Ownership、Authorization、State、Capability、Transfer 及跨 Runtime 的语义和引用边界。它不要求训练基础模型，不规定向量数据库、记忆检索算法、模型路由、Skill Engine 或 Workflow Engine。参考实现复用执行平台，通过 Adapter 接入。

Avatar 是个人长期 AI 状态的有限数字表示，不是人的完整定义、意识副本或人格复制。模型与 Runtime 可替换，不同个人长期形成的状态不可视为彼此可互换。个人控制权也不意味着自动取得第三方内容、公司资料或 Skill 源码的权利。

| 架构部分 | 保存内容 | 规模与加载方式 |
| --- | --- | --- |
| Personal State | 偏好、记忆、知识、项目与关系语境 | 可增长；按任务与授权加载 |
| Avatar Core | 身份引用、核心摘要、索引、扩展清单、完整性信息 | 紧凑；支持独立验证与迁移 |
| Procedural State | Workflow、Capability 引用、Skill 使用状态、Trace 摘要 | 可增长；通过索引与 Resolver 解析 |

1 2 本次扩展的位置

多成员容器是 Core 外部的组织和打包结构。生活、个人工作、组织空间是状态访问边界。记忆生命周期是状态治理规则。这些扩展不得将完整历史、所有成员资料或所有组织内容塞进 Avatar Core。

Core 中的 profile_summary 也可能包含私人信息，不能因为体积小就默认完整提供给所有 Runtime。运行时应生成 Authorized View，只披露当前任务获准使用的核心字段、索引和状态片段。

1 3 协议与参考实现

协议层保存事实、契约与可迁移语义；Adapter 转换状态和能力；Agent Runtime 完成规划与执行。本文所称参考 Core Service / Runtime 是状态与策略服务，不是重新开发一套 Agent 引擎。OpenClaw 是首个验证目标，不构成协议依赖。

界面形态、电子宠物、市场和结算保持独立扩展。AIAP 不定义 ACU 或任何货币体系；未来只通过 External Account Binding 或独立扩展建立连接。

2 Avatar Core 与身份连续性

本版保留 v0.4.1 的 Core 最小字段方向，新增业务语义优先放入版本化扩展或被引用的 manifest。User Core 指归属于某个用户的 Avatar Core，不新增一套与 avatar_id 竞争的身份体系。

| 已有字段 | 职责 |
| --- | --- |
| aiap_version / avatar_id | 声明协议版本与稳定 Avatar 标识 |
| owner / identity_refs | 控制权主体、身份与密钥证明引用 |
| profile_summary | 经确认的高密度核心摘要，仍受分域权限约束 |
| state_index / procedural_index | 个人状态与程序性状态的索引及引用 |
| extensions | 扩展 namespace、版本、依赖与兼容要求 |
| integrity / updated_at | 完整性证明及版本更新时间 |

2 1 身份与所有权

必须区分 Human Owner、Avatar、当前操作者以及 Custodian / Runtime。avatar_id、文件持有或管理员账号都不是所有权证明。Owner Key 与 Avatar Key 逻辑分离；受保护身份变更必须验证授权，不能从聊天、记忆或模型推断中自动产生。

延续密钥轮换、撤销与恢复机制。恢复必须记录证明链和审计信息；新密钥不得仅凭旧备份自行取得当前权限。凭据和私钥由独立安全组件管理，Core 只保存必要引用。

2 2 Resolver 与外部账户

Identity Resolver 连接可验证身份方法；State Resolver 定位 Core、manifest 及扩展状态。解析出的对象须验证来源、版本、权限、完整性和撤销状态。引用可定位不代表允许读取；离线或缺失对象应返回明确状态。

External Account Binding 保存账户类型、账户引用、验证方式、权限和状态，不保存明文秘密。Credential / Proof Extension 继续预留选择性披露等机制，具体密码学 Profile 另行定义；本版不宣称已实现这些机制。

2 3 版本与更新

每次持久状态更新应关联对象版本、前一版本与变更来源。Core 摘要由获准的状态生成，必须保留来源引用。受保护身份、授权和核心摘要不接受未经验证的 Runtime 直接覆盖。

3 多成员容器与共享空间

Multi-Core Container / Avatar Bundle 是多个逻辑独立 Core 的物理组织容器，可用于家庭、本地 NAS 或组织部署。基本原则是物理聚合、逻辑独立、授权分离。单成员容器是其退化情形，第一版无需启用多成员界面即可沿用相同模型。

| 对象 | 建议承担的语义 | 不得推导出的权限 |
| --- | --- | --- |
| Bundle Manifest | 容器标识、Core 引用、Shared Space 引用、版本与完整性 | 持有容器不等于拥有所有成员 |
| User Core | 独立 avatar_id、owner、状态索引与授权 | 一个成员不得读取另一成员 |
| Membership | 成员、空间、角色、有效期与状态 | 加入组织不合并个人 Core |
| Shared Space | 共享对象、控制主体、ACL 与 Consent | 容器管理员不自动获得正文读取权 |

3 1 分离与备份

容器必须支持按 Core 选择导出、备份和恢复。导出 manifest 应区分随包携带的对象、保留的外部引用、被排除对象和未解析依赖。分离一个 Core 不得修改其他成员的身份或复制其数据。

Shared Space 中的内容默认保持原有归属。个人迁出时，可以携带获准的引用或经明确授权的副本；不能因过去有读取权就自动取得永久导出权。需要独立恢复时，必须检验引用依赖是否已完整保存。

3 2 管理与保护

容器管理、存储运维、内容访问和授权管理应分别授予。针对普通应用的逻辑隔离可由策略层实现；如果部署目标包括防止宿主机管理员读取数据，须增加独立密钥管理和相应加密边界，单靠 ACL 不足以实现。

每个 Core 与 Shared Space 应具有独立的授权和密钥作用域，容器索引也须限制披露，避免泄露成员名称、项目存在性或私人关系。不得在共享 manifest 中明文保存全体成员的敏感摘要。

3 3 家庭与公司

家庭成员的私人空间不因家庭关系开放；监护或代理访问须有明确授权规则。公司成员的工作空间与个人 Core 保持分离。离职或退出空间应撤销成员权限与运行凭据，保留个人合法可迁移状态，不自动带走组织业务内容。

4 生活与工作分域授权

同一个人的身份保持连续，状态可以按使用场景隔离。访问控制不能仅依赖“生活”或“工作”标签；每个对象需要明确的归属主体、空间引用及策略引用，所有读取、检索、摘要和写入均需执行策略。

| 范围 | 典型内容 | 默认访问边界 |
| --- | --- | --- |
| 通用个人偏好 | 语言、每次一步、输出格式 | 用户明确允许的场景复用 |
| 个人生活 | 家庭安排、健康、兴趣、私人沟通 | 个人生活会话 |
| 个人工作 | 职业目标、个人学习计划、工作习惯 | 个人工作会话 |
| 组织业务 | 客户资料、合同、内部项目与流程 | 当前组织或项目授权空间 |
| 家庭共享 | 共同日程、家庭购物和协作事项 | 获授权的家庭成员 |

4 1 最小访问决策

访问决策应至少考虑操作者身份、资源归属、空间成员关系、动作、用途、授权有效期、撤销状态及当前会话。read、write、share、export、delete 和 admin 必须可区分；允许读取不自动允许向其他人分享或向外部模型传输。

工作场景默认查询通用偏好、个人工作域及明确选中的组织空间。不同公司的业务空间也必须相互隔离。模型自动识别场景只能提出建议，不能自行扩大授权。范围不明确时，持久写入进入待确认状态。

4 2 跨域与最小披露

跨域任务须获得来源空间的相应授权。安排出差若只需要私人日程的可用性，可返回“该时段不可用”，不提供私人事项正文。降敏结果仍可能敏感，必须重新判断可披露范围，不能把摘要视为天然公开信息。

偏好采用“适用范围内的明确选择优先”原则，具体工作偏好可以覆盖通用风格。偏好不得覆盖权限策略；明确拒绝和撤销必须阻止访问，模型不得通过合并其他记忆绕过。

4 3 派生内容与上下文

摘要、向量、缓存、Trace 与 Learned Workflow 必须继承来源限制。多来源派生对象默认采用共同允许的范围；扩大范围需单独授权。会话切换域时应重建上下文，避免此前加载的私人内容留在工作会话或共享缓存中。

5 分层记忆模型

本版沿用 AIAP State Model v0.1 的 M0 至 M3。这里的 M1 Working Memory 指活跃任务记忆，不等于职业或公司记忆。生活与工作都可以具有 M1、M2、M3；不能把生命周期与业务范围混为一谈。

| 逻辑层 | 含义 | 持久化和加载规则 |
| --- | --- | --- |
| M0 会话临时 | 当前输入、临时计划、即时工具结果 | 可选导出；不默认晋升为长期记忆 |
| M1 活跃任务 | 近期项目、未完成事项与活跃上下文 | 按任务相关性加载；复核后晋升或归档 |
| M2 长期记忆 | 稳定偏好、重要决策、长期知识 | 保存来源与有效性；受控更新 |
| M3 归档 | 旧项目、历史决策与低频资料 | 通常不主动注入；授权后按需检索 |

5 1 四个独立维度

访问范围回答“谁在什么场景可以使用”；记忆层级回答“持续多久、怎样参与任务”；对象状态回答“候选、有效、被替代、撤销或删除”；Runtime 缓存回答“放在哪里、读取多快”。M3 是逻辑归档，不等于必须放在某种冷存储设备。

Semantic、Episodic、Project 等内容类型也不等于层级。Procedural State 保持独立的一等状态类别，通过 Workflow 和 Capability 表达做事方法，不退化为一段普通记忆文本。

5 2 最小元数据

记忆应具有稳定标识、内容或引用、来源、置信度、归属、空间、层级、对象状态、创建及更新时间。生命周期策略可使用 importance、recall_count、last_used_at、pinned、recurrence、expected_next_use 与 last_verified 等事实；字段名与可选性在后续 Schema 修订中确定。

来源必须区分用户明确陈述、观察、推断和导入。模型推断不得伪装成用户事实；重复检索也不能提高其事实权威等级。旧事实应能被更正或标记为被替代，同时保留必要的来源链。

5 3 受控写入

Runtime 输出 StateDelta 候选，经 Schema 校验、权限判断、来源检查和必要确认后写入状态库。明确要求记住的信息可以按既定策略入库，但仍需确认所属范围。稳定状态进一步进入 Core 摘要时，应再次验证其适用性与最小披露要求。

6 记忆降级归档与遗忘

AIAP 保存可迁移的生命周期事实和策略引用，不固化统一的 activity score、衰减公式或 HOT / WARM / COLD 阈值。目标 Runtime 可根据资源和任务重新计算缓存，但必须保留固定、归属、来源与删除等语义。

| 变化 | 触发条件 | 必须保留的边界 |
| --- | --- | --- |
| 候选成为有效记忆 | 来源充分且通过授权或确认 | 推断不能静默替代用户陈述 |
| M1 晋升为 M2 | 持续价值、重复任务价值或用户指定 | 记录晋升依据和对象版本 |
| M1 或 M2 转入 M3 | 低频、任务结束且满足归档策略 | 不降低权限，不等于删除 |
| M3 重新激活 | 当前任务需要或用户要求 | 重新检查有效性与访问授权 |
| 对象被替代 | 新事实或偏好覆盖旧版本 | 保留版本关系，避免两版冲突注入 |
| 撤销或删除 | 有权主体提出并通过规则校验 | 处理原文、索引、缓存与派生副本 |

6 1 自动降级的保护条件

显式固定的记忆、稳定偏好、身份与授权规则不得仅因长期未访问而自动降级失效。周期性事项必须考虑 recurrence 与 expected_next_use。年度任务虽然低频，仍可能有高价值。

参考实现可采用可配置时间窗：对长时间未使用、未固定、无未完成任务引用且近期无预期使用的内容提出归档。时间窗属于本地策略，不是协议常量。自动执行前应保存变更原因与回退信息。

6 2 检索与使用统计

后台扫描、批量索引不应被当作真实使用。建议区分检索命中、进入上下文和用户确认有用，避免系统反复召回同一条内容使其永不降级。摘要失败或低置信度内容不应因压缩而丢失原始证据。

6 3 撤销与删除

撤销访问立即作用于后续请求，并使相关缓存和会话授权失效。删除需处理正文、向量、摘要、缓存及派生引用；恢复旧备份前应应用当前删除与撤销记录。审计保留应最小化，不能以审计名义继续保存全部已删除正文。

已合法披露到不受控外部系统的数据无法仅靠本协议远程收回。实现应明确受控副本、外部副本、备份清理窗口与删除完成状态；不能把检索不到描述为数据已物理删除。

7 程序性状态与适配器

保留 Procedural State Protocol v0.1 的解耦关系：WorkflowDescriptor 引用 Capability，RuntimeBinding 再连接具体 Skill、Tool、Agent 或 API。Capability 是一等协议对象；可移植流程不得依靠某个厂商的私有 Skill 名称表达其语义。

Capability Mapping 继续使用 exact、compatible、partial、composite、unresolved 五类结果。部分可用或无法解析不能静默标记为完全等价。第三方 Skill 源码的权利不因 Avatar 保存使用记录而转移。

| Adapter v0.1 接口 | 本版补充约束 |
| --- | --- |
| inspect_runtime | 报告实际能力与隔离能力；不夸大兼容性 |
| compile_context | 只编译已授权对象；绑定任务和空间范围 |
| resolve_capability | 同时检查能力语义、依赖及执行权限 |
| execute_workflow | 沿用当前授权，权限变化后须重新检查 |
| emit_trace | 记录可观察动作及结果摘要，并继承来源限制 |
| export_delta | 仅生成变更候选；声明归属、来源及基础版本 |

7 1 双向状态流

进入 Runtime 的是获授权状态片段；返回 AIAP 的是 ExecutionTrace 和 StateDelta 候选。StateDelta 在验证前不构成持久修改。执行成功不代表有权长期保存全部输入，也不代表可以把组织业务经验复制到个人生活域。

7 2 工作流学习

从重复执行轨迹提炼 Candidate Workflow，经验证或用户确认后成为可复用流程。私人或组织 Trace 提炼出的 Workflow 默认继承原范围。去掉客户姓名不自动解除商业内容限制，扩大共享范围须另行判断与授权。

7 3 兼容等级

沿用 Adapter v0.1 的 AIAP-L1 Context Compatible、AIAP-L2 Capability Compatible 和 AIAP-L3 Native Avatar Compatible。L2 包含 L1 要求；L3 还要求原生状态语义与受控同步。本版新增安全要求应单独列出测试结果，不能以等级名称代替验证。

State Model v0.1 另有 State Reader / State Runtime / Portable Runtime 的等级表述。这是另一套评估维度，不与 Adapter L1 至 L3 自动等同；兼容声明必须写明所依据的规范名称和版本。

8 安全迁移与独立恢复

Secure Avatar Transfer 继续属于 Core Protocol。复制文件不是证明所有权，备份恢复也不等于完成跨平台安全迁移。Transfer Certificate 必须约束 owner、avatar、source、destination、nonce、有效期、范围及证明；消费状态须持久化，防止重放。

8 1 迁移流程

接收方发出挑战后，来源方列出待迁移 Core、对象范围、组织限制及缺失依赖。授权主体确认并签署本次范围；接收方验证身份、目的地、时效、撤销、证书完整性及对象清单后，先进入隔离导入区，再提交可用状态。

Core-first Transfer 先迁移紧凑 Core 与必要清单；Personal State 和 Procedural State 可 Lazy Migration。每次后续解析仍需检查权限，不因最初通过 Core 验证而永久取得所有引用对象。失效的能力绑定必须重新解析。

8 2 分范围迁移

本版要求迁移授权可以精确绑定某个 Core、空间、对象集合和操作模式。清单摘要及范围必须受到签名保护；若既有证书结构不足，应通过版本化扩展或新 Profile 定义，不能仅加入未签名的筛选参数。

复制、设备迁移和控制权转让是不同操作，必须分别声明。迁移到新 Runtime 不自动改变 Owner，也不自动删除源端或撤销其权限。源端撤销和删除需执行单独策略并记录结果。

8 3 多成员与组织空间

整包备份不得成为绕过成员授权的途径。每个 Core 的授权独立验证；共享空间还需满足相应控制主体的导出规则。个人有权迁移自己的 Core，不意味着有权带走公司客户列表、同事资料或组织密钥。

恢复个人 Core 时，组织引用可以保留为待重新授权的引用；不得沿用备份中的过期成员资格。Shared Space 不可用时应报告依赖缺失，不能将恢复结果标记为完全可用。

8 4 加密与失败恢复

证书证明授权，独立加密机制保护敏感载荷。序列化、摘要与签名规则应由安全 Profile 明确定义。导入过程应支持事务或等效提交机制、幂等重试与失败回滚，避免半个容器被激活。未知关键安全扩展必须拒绝激活。

独立离线备份包含获准且完成完整性验证的实际对象；仅导出 Core 和外部链接只能保证引用可携带，不能保证离线完整恢复。导出报告必须区分这两种保证。

9 存储检索与更新边界

9 1 权威状态与使用副本

参考实现以 Core 及其引用的状态库共同构成权威持久状态。Core 不是全部记忆的数据库。OpenClaw 中的上下文文件和向量索引属于适配后的使用副本；长期变更通过 StateDelta 回写，不能由多个副本无条件相互覆盖。

USER.md 等文件可能被 Runtime 自动加载。不得把所有域的完整记忆写入同一个全局加载文件。通用偏好仅写入获准共享的子集，生活、工作和组织内容通过任务范围内的上下文投影使用。

9 2 检索安全边界

在数据进入模型、排序器、摘要器或其他外部组件前，先限制可访问对象集合。实现可以采用分区索引或可靠的带权限过滤检索；不能先让模型读取全部命中内容，再要求模型自行忽略越权结果。

索引条目应绑定空间、来源对象版本和策略版本。缓存键应包含身份与授权范围，撤销时失效。向量和元数据可能泄露内容或存在性，不能视为公开数据。Embedding Provider 同样是数据接收方，必须受处理范围与出域策略约束。

9 3 冲突处理

StateDelta 应携带基础版本和来源。并发修改使用版本检查；非冲突字段可按规则合并，语义冲突进入待处理状态。不得仅按最后写入时间覆盖用户明确偏好、身份或权限。

迁移或导入时，未知但非关键扩展可原样保留并禁用使用；未知安全限制不得忽略。缺少来源、归属或权限的旧对象进入隔离区，待人工或受信迁移规则分类。

9 4 参考部署

现有 N4100 / 飞牛 Docker 可承载首个 Core Service 与 OpenClaw Adapter 验证环境；已配置的 Ollama embedding 服务可继续用作检索后端。部署位置属于参考方案，正式目录、挂载和权限应依据现场配置确定。

Memory 已完成的写入、向量检索与重启测试，只证明现有检索链路可用。它没有验证 AIAP 身份、多成员隔离、生命周期治理、迁移证书或跨 Runtime 兼容性，这些必须单独验收。

10 兼容策略与实施范围

v0.4.2 是总白皮书修订号。State Model v0.1、Procedural State v0.1、Adapter v0.1 与 Runtime v0.0.1 各自独立演进，不能通过修改一个 aiap_version 字符串宣称兼容。

10 1 Schema 衔接

现有 aiap-state.schema.json 将 aiap_version 固定为 0.1，以 domains 表达状态域，并关闭根对象 additionalProperties。生活与工作是访问作用域，不应直接冒充新的根字段或替换 aiap.memory 等已有域。

新增容器清单、空间引用、来源继承与生命周期策略应通过版本化扩展或显式 Schema 修订落地。extensions 可容纳命名空间化数据，但仅能解析扩展字段不代表具备相应安全语义。声明为必需的隔离策略不能被旧实现静默忽略。

| 阶段 | 实现内容 | 通过后能声明什么 |
| --- | --- | --- |
| A 单成员基础 | Core、身份验证、状态索引、分域策略、M0 至 M3、受控 StateDelta | 单成员分域状态闭环 |
| B 备份恢复 | 选择性导出、manifest 校验、独立测试恢复、删除记录处理 | 获准范围内可恢复 |
| C 安全迁移与能力 | 证书验证、防重放、Capability Mapping、Trace 与 Workflow | 对应迁移及 L2 测试通过 |
| D 多成员扩展 | Bundle、Shared Space、成员撤销、逐 Core 分离 | 通过测试的家庭或组织场景 |
| E 第二 Runtime | 独立适配器与能力、状态连续性评估 | 实测的跨 Runtime 可携带性 |

10 2 第一阶段必须保留的接口

即使只有一个成员，读写请求也应包含验证后的主体、目标 Core、空间、动作和用途；持久对象必须有归属和策略引用。容器可以只有一个 Core，Shared Space 管理界面可暂缓，但底层不能假定永远只有一位用户。

第一阶段不承担复杂工作流自动学习、完整企业管理后台、全球能力目录、市场与结算。身份和隔离基础不能以功能暂缓为由省略。旧版 v0.5 第二 Runtime 路线继续保留，本次 v0.4.2 不占用该里程碑。

11 验收与失败条件

以下是参考实现的待执行验收清单，不是已经获得的测试结果。安全边界测试优先于演示效果；任一未授权内容进入上下文、工具输出或导出包都应判定该项失败。

| 验收项 | 测试方法与通过标准 |
| --- | --- |
| 单成员连续性 | 写入明确偏好，重启并开启新会话，保留来源与同一对象标识 |
| 生活与工作隔离 | 在生活域置入测试事实；工作查询、摘要和缓存均不可泄露 |
| 组织间隔离 | 同一用户加入两个测试组织，A 的任务不能读取 B 的内容 |
| 跨域最小披露 | 只授权日程可用性，返回忙闲信息而非私人事项正文 |
| 候选与冲突 | 推断偏好或过期版本更新不能覆盖已确认的用户偏好 |
| 生命周期 | 模拟长期未使用；普通对象可归档，固定和周期对象遵循保护规则 |
| 撤销与删除 | 预热索引及缓存后撤销；新请求失败，恢复备份也不能复活授权 |
| 逐 Core 分离 | 测试容器中两位成员独立；分离 A 不带走 B 的正文或私有索引 |
| 组织退出 | 撤销成员关系后，旧链接、旧会话和导出请求不能继续读取 |
| 安全迁移 | 篡改范围、替换目的地、重放证书、使用过期证明均被拒绝 |
| 恢复完整性 | 缺失引用被明确列出；签名或摘要不符的对象不激活 |
| 程序性连续性 | 保留 Workflow 语义；五种映射结果明确，无静默能力升级 |

11 1 测试记录

每项记录版本组合、输入范围、预期、实际结果和失败原因。先使用合成成员及非敏感测试内容。单环境导入导出不能替代第二 Runtime 的实测；本地备份通过不能替代 Secure Avatar Transfer。

11 2 评估方式

可延续程序性状态规范的 WCR、CMR、PCR、TSR、TER 和 TTAR 评估方向，具体口径与基线另行固定。隔离、撤销、防重放采用明确的通过或失败门槛；本白皮书不提供未经测试的性能数字或兼容性结论。

12 1 建议下一步规范工作

形成 Multi-Core Container、Space and Consent、Memory Lifecycle、Scoped Transfer 四组配套规范。明确字段、签名覆盖范围、关键扩展协商与错误码后，再更新 Schema、示例、迁移工具及测试夹具。本文中的建议字段尚不构成可直接替代现有 Schema 的正式文件。

概念数据关系为：Bundle 引用多个 Core 和 Shared Space；每个 Core 关联独立 Owner，并通过索引引用状态对象；每个对象绑定空间、来源、版本及策略；Adapter 取得 Authorized View 并提交 StateDelta 候选。共享空间不得因被多个 Core 引用而复制或合并其所有权。
